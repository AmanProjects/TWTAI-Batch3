Day 8—Plugin anatomy: every component, end to end

Expert Module 8 2 hours Two tracks Claude Code
Full lesson

This page is the workshop summary and agenda. For the complete lesson text, open the engineering track lesson or the writers' track lesson.

Overview

Ship your team's standard as a plugin

The final day is the deepest. You will see every plugin component type, read a real plugin.json manifest, understand loading, scopes, and the command-line interface, and build a working multi-component plugin. The writers' track focuses on packaging a house style standard; the engineering track covers the full thirteen-component anatomy and the Agent Plugins portability spec.

Plugins are a Claude Code feature

Building, validating, and installing plugins happens in Claude Code. There is no browser equivalent for authoring a plugin. The writers' track keeps the code to a minimum, but a local environment is required for this day.

Choose your track

Writers' track and engineering track

Writers' track · primary

Ship your standard

Read the house-style plugin, then build your own three-piece plugin—a skill, a hook, and a small helper—add a value teammates are asked for on install instead of hand-editing files, and publish it so a colleague can run it cold.

Engineering track · optional depth

Full anatomy

Walk all thirteen component types, the complete manifest schema including userConfig and dependencies, the three path variables, caching and versioning, and port your plugin to the Agent Plugins v1.0.0 cross-client spec.

Learning objectives

By the end of this day you can

  • Explain what a plugin is and what belongs inside one, in plain language.
  • Pick the right piece for a job: skill, command, agent, hook, or tool.
  • Say why every extra piece costs your team tokens in every conversation.
  • Build, validate, and test a three-piece plugin.
  • Publish it and get a teammate running it.
  • Set up a value teammates are asked for on install, instead of hand-editing files.

A warning worth repeating

Every component costs tokens, always

The budget nobody tells you about

Each piece a plugin adds is loaded into context in every conversation, whether or not it is used. A lean plugin that does one thing well beats a kitchen-sink plugin that slows every session. Add a component only when it earns its place.

Doing it on the web

Claude.ai web alternatives

Claude Code (as written)

Load a plugin with claude --plugin-dir, inspect with claude plugin details, scaffold with claude plugin init ... --with skills hooks, then validate and install.

Claude.ai web interface

There is no plugin authoring in the browser. The closest web equivalent to "ship your standard to the team" is an organization-provisioned Skill: a Team or Enterprise admin publishes a Skill once and everyone gets it, with a value requested at setup. You lose hooks and commands, but you keep the core—a shared standard, centrally distributed.

Homework and next steps

After the program

  • Publish your plugin or your org Skill and get your whole team onto it.
  • Write your personal AI integration plan—see the playbook.
  • Keep one skill under active maintenance and review it monthly.

Checklist

Expert checklist

  • I built and published a working multi-piece plugin or org Skill.
  • A teammate ran it cold on their own machine.
  • I can justify every component it contains.
